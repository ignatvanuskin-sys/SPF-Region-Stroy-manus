# 2. LEADS — куда сохраняются заявки

**Сейчас (VERIFIED локально):** `server/data/leads.ndjson` + фото в `server/data/uploads/`.

**Проблема:** на контейнерном хостинге эта папка эфемерна — при каждом передеплое заявки исчезают. Поэтому:

- сервер принимает каталог из `LEADS_DIR`;
- в `/api/health` есть `storage.persistent` — `true` только если `LEADS_DIR` задан явно (то есть смонтирован постоянный диск);
- при старте в лог пишется предупреждение, если постоянное хранилище не подключено.

**Рекомендация (самый простой надёжный вариант):** один постоянный диск Railway, смонтированный в `/data`, плюс переменная `LEADS_DIR=/data`. Это без отдельной БД, без новых зависимостей и без изменений кода. PostgreSQL/ Supabase здесь избыточны: объём — единицы заявок в день, а лишний сервис — лишняя точка отказа.

**Что нужно от вас:** включить план Railway и добавить диск — после этого одна команда `railway volume add -m /data` и `railway variables --set "LEADS_DIR=/data"`.

- вебхук **не выдуман**: без переменной канал честно сообщает `not configured`.

Telegram — самый быстрый способ начать получать заявки без CRM: создать бота у @BotFather, задать два значения, и менеджер получает сообщение в чат.

# 4. ГЛАВНОЕ ТРЕБОВАНИЕ: НИКАКОГО ЛОЖНОГО УСПЕХА

Реализовано три исхода, и клиент видит честный текст для каждого:

| Исход | Когда | Что видит клиент |
|---|---|---|
| `delivered` | Хотя бы один канал (CRM/Telegram) принял заявку | «**Заявка передана менеджеру**» + номер заявки |
| `stored` | Заявка сохранена, но каналы не настроены или упали | «**Заявка сохранена**» + предложение написать в WhatsApp, чтобы ускорить ответ |
| ошибка (503) | Не сохранилось **и** не доставлено | Красный блок: заявка сохранена на устройстве, кнопки WhatsApp и «Позвонить» |

**Доказательство (VERIFIED, реальные запросы):**

```
POST /api/leads (валидная заявка)          -> 201  outcome":"stored"  storage":{"saved":true
POST /api/leads (без согласия)             -> 400  {"ok":false,"error":"consent is required"}
POST /api/leads (хранилище недоступно)     -> 503  {"ok":false,"error":"Could not accept the request"}
```

Третья строка — ключевая: каталог заявок был специально сломан (путь внутри файла), сервер **не сохранил** заявку, каналов доставки нет — и вместо мнимого «успешно отправлено» вернул **503**, а UI показывает ошибку с запасными способами связи.

# 13. ФИНАЛЬНЫЙ СТАТУС

## 🟡 READY TO SHOW CLIENT — и ⛔ BLOCKED для производства

**Сайт готов к показу владельцу:** он собран, линт чистый, консоль чистая, битых ссылок нет, мобильная и десктопная вёрстки проверены, заявки корректно принимаются локально, ложный успех исключён, безопасность и SEO в порядке.

**Взять реальных клиентов он пока не может** — и это не про качество сайта. Две внешние вещи не в моей власти:
- **некуда деплоить** (Railway требует оплаты плана, Netlify не запускает Node-сервер);
- **заявке некуда доходить** (канал доставки не настроен).

Поэтому статус **BLOCKED**: пока «посетитель → заявка → гарантированно у бизнеса» не замыкается, статус READY FOR PRODUCTION был бы неправдой.

**Что снимает блокер за один шаг:** оплатить Railway (или дать токен другого хостинга с поддержкой контейнеров) **и** включить Telegram-бота или вебхук CRM. После этого — деплой, `railway volume add -m /data`, `railway variables --set "LEADS_DIR=/data"`, тестовая заявка с пометкой и проверка, что она дошла.
